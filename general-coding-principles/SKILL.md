## 程式開發核心準則 (Core Coding Principles)

### 1. 命名與風格約束

- **命名一致性**：修改程式碼前，必須遵循既有檔案的命名慣例（如 CamelCase 或 snake_case）
- **需求導向**：先完成功能實作，再提出命名或檔案拆分等等的重構建議
- **區塊寫作**：撰寫業務邏輯或測試案例時，須遵守 AAA 模式，讓程式碼有清楚的區塊分隔
- **if/else 縮寫**：if/else 區塊使用 `{}` 分行撰寫

### 2. 結構與品質控制

- **SOLID 原則**：在當前專案架構下盡可能遵守 SOLID 原則
- **長度控制**：每個函式/類別僅處理單一邏輯，若單個函式超過 50 行，必須評估是否拆分
- **防禦性工程**：關鍵路徑必須包含 `try-catch` 或錯誤檢查，嚴禁忽略潛在的 Null 指標或異步錯誤
- **依賴最小化**：優先使用內建庫或專案既有套件，安裝任何外部依賴時先詢問

### 3. 註解與文件規範

- **必要的註解**：僅針對複雜邏輯或 Workaround 撰寫 `Why` 類型的註解
- **冗餘註解**：顯而易見的程式碼不需要撰寫逐行註解（如 `i++ // i 加一`）

### 4. 靜態分析與安全性

- **忽略非業務層面的 lint**：忽略排版、空格、import 順序等不影響邏輯的 lint 警告
- **高風險警告**：涉及記憶體洩漏、安全性漏洞或 Race Condition 的提示，必須先回報並取得同意後才進行修復
- **嚴禁 hardcode**：禁止將任何 API Keys、Password 或 Sensitive Tokens 等敏感資訊直接寫入程式碼

### 5. 執行工作流程 (Execution Workflow)

- **上下文檢索**：修改任何檔案前，必須先確認該檔案及其相關檔案的上下文，理解開發脈絡
- **最小變動原則**：僅修改與任務直接相關的程式碼，重構要在目標任務結束後提出建議並詢問
- **測試**：若目錄中存在 `/tests`，在提交程式碼前必須主動詢問是否需要撰寫或更新對應的測試案例
- **清理**：任務完成前，必須移除所有 console 資訊（`print`, `console.log`），改動或試驗中遺留的廢棄程式碼片段也要移除
